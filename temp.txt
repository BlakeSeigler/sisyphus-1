Register File (register.v) — Explanation
==========================================

Status: register.v is currently an empty stub. This corresponds to M2 in
TODO.md, which has not been implemented yet.

What it's for
-------------
It's the CPU's bank of 32 general-purpose registers (x0-x31), each 32 bits
wide. Every RV32I instruction that isn't purely memory/immediate reads its
operands from here and writes its result back here — it's the fast scratch
space sitting between instruction decode and the ALU/memory stages.

One instance, not reused per-instruction
-----------------------------------------
There is exactly one register file in the whole CPU. It's instantiated once
inside cpu_core.sv (per the current skeleton) and every instruction,
regardless of type, goes through that same single instance — decode just
drives different address/control values into it each cycle. Contrast this
with something like the ALU, which is also a single instance but is
combinational and stateless; the register file is a single instance that
holds state across cycles.

How it behaves
---------------
- Reads are combinational — in a single-cycle design, the instruction is
  decoded and its operands must be available in the same cycle the ALU uses
  them. So rs1/rs2 -> data out has no clock edge in the path.
- Writes are synchronous — the result of an instruction gets committed to rd
  on a clock edge (so instruction N+1 doesn't see it appear mid-cycle and
  start using it early).
- x0 is hardwired to zero — reads of register 0 always return 32'b0 no
  matter what, and writes to register 0 are silently discarded. This isn't a
  real storage cell; it's just special-cased in the read/write logic.
- The "write-then-read same cycle" test called out in TODO.md is
  specifically checking: if an instruction writes rd and, same cycle, a
  later combinational read asks for that same address, what do you get — the
  old value or the newly written one? That's a design decision to pin down
  (write-first vs. old-data-first) before M5 wires everything together,
  since forwarding-adjacent bugs here are a classic single-cycle gotcha.

The "buttons" (ports) it needs
--------------------------------
Port        Width  Direction  Purpose
clk         1      in         clocks the synchronous write
rs1_addr    5      in         which register to read on port 1 (2^5 = 32 regs)
rs2_addr    5      in         which register to read on port 2
rs1_data    32     out        combinational read-port-1 output
rs2_data    32     out        combinational read-port-2 output
rd_addr     5      in         which register to write
rd_data     32     in         value to write into rd
reg_write   1      in         write-enable — only commit rd_data if this is
                              high (comes from the control unit; e.g.
                              branches/stores don't write a register)

That's the minimum set: 2 combinational read ports, 1 synchronous write
port, gated by a write-enable, with x0 special-cased — matching the M2
bullet exactly. No reset is architecturally required (RV32I doesn't mandate
defined register state at boot), though some designs add one anyway just to
get clean, deterministic waveforms in simulation — that's a judgment call,
not a spec requirement.
